# 002: Sync (phase 4, 2026-10-30)

Read from `imputnet/helium-chromium` (`patches/helium/core/sync/`, `settings/sync-setup-contract.patch`; same files at our pinned rev 2 `58261a2` and at HEAD `2f81b9c`, rev 3) and `imputnet/helium-services` (HEAD `110144e`). Not built or run separately; it is compiled into our phase 1 tree.

- **Vault format:** one vault = a mutable object `head` plus immutable objects named by the hex SHA-256 of their ciphertext. `head` points at the newest commit; commits form a hash chain (generation, parent digest). Each epoch starts with a full snapshot, later commits carry deltas; a new epoch after 64 commits or enough bytes, old epochs are garbage collected. Payloads over 4 MiB go to separate chunk objects. Records are proto2 (`SyncVaultHead`, `SyncVaultCommit`). The payload is the state of Chromium's own in-memory sync server (loopback server), so the stock sync engine merges bookmarks, passwords etc.
- **Encryption:** one random 32-byte vault key. Object key = HKDF-SHA256(key, salt = vault UUID). AES-256-GCM-SIV, random 12-byte nonce, associated data = label + UUID + object role. The browser keeps a local checkpoint (generation + digest) and rejects rollback and forks.
- **Transport:** no network protocol. The browser asks an *extension* (new `syncVaultProvider` API) to list/create vaults, read objects, write them with compare-and-swap on a revision, and collect old epochs. Key handling: either a recovery key the user saves, or the extension wraps the vault key with its account (then the provider can read the key).
- **Server:** none. helium-services has bangs, extension proxy, crash dumps, push, uBO and nginx; no sync. No provider extension ships in the series.
- **End to end:** no. The extension API is behind `kApiSyncVaultProvider` (disabled by default), there is no provider, and only the settings mojom contract exists (no handler, no page). No device list, no device approval, no revocation.

**Recommendation (taken):** reuse Helium's vault format and encryption byte for byte, and write our own self-hosted server whose object API maps 1:1 onto Helium's transport (so phase 7 keeps Helium's engine and only adds a transport). Add what PROJECT.md 4.6 needs and Helium lacks: token registration, per-device credentials and revocation, device approval with a comparison code, key rotation after revocation, and a device roster inside the vault. Never use the provider key-wrapping path (it gives the server the key). Spec: `sync/protocol/SPEC.md`.
